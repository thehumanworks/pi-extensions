# Fable high-effort review 1

Review complete. Everything below is from reading the sources; I ran nothing and changed nothing, per the brief.

## Verdict

The longitudinal protocol is well scoped, but as currently wired it cannot answer three of the user's expanded questions, and one capture defect will silently bias the long and dream arms. Fix findings 1 to 3 before `--mode=history` runs, or the results will measure the wrong thing.

## Findings, by priority

**1. Critical, new defect: the correction sessions are never captured.** History mode runs each stage as its own print-mode session with non-forced capture at shutdown (`eval/long/run.mjs:84-85`, `index.ts:149`). Non-forced capture is gated by the salience regex at `src/capture.ts:72`, which looks for words like remember, always, never, don't. Neither correction prompt contains any of them (`eval/long/fixtures.mjs:8` and `:27`), and both are far under the length threshold. So the capture skips, advances the watermark (`src/capture.ts:159-162`), and the batch-size and retry corrections are never stored or superseded. Even under forced capture, both corrections contain the word "temporary", which trips the per-entry temporal cue at `src/capture.ts:78` and `:237-240`, so every candidate citing that entry is dropped for lacking a grounded expiry. That per-entry cue is a design bug in its own right: one temporary remark in a user message discards all durable facts in the same message. Consequence for inference: long and dream stores hold only the stale decisions, the supersession path is untested, and the correction reaches those arms only through the 600-byte recent window (`run.mjs:87`, `:105`). Check: drive `CapturePipeline.capture` with the stub-model pattern from `test/capture.test.ts` using the exact correction text and a candidate citing that entry. Expect saved to be zero in both the non-forced and forced cases. Then widen salience and make the temporal cue per candidate.

**2. High: the dream arm measures duplicate injection, not generalization.** Model-written abstractions go only to JSON hypotheses (`src/dream.ts:232`) and never enter recall. What does enter the store is the automatic parent, whose body is the full statement list of every source (`src/dream.ts:215-219`). Factoring only saves bytes when identical sentences of 48 or more characters repeat across sources (`src/dream.ts:87`), which the unit fixture guarantees and real captures rarely will. Otherwise the parent is smaller than the rendered sources only by per-item header overhead, and active bytes roughly double for the grouped items. Automatic recall has no derivation-aware exclusion (`src/retrieve.ts:52-63`, `index.ts:131`), so a parent and its sources can both be injected into the same 1,200-byte budget. The dream arm will therefore tend to score at or below the long arm for reasons unrelated to dreaming. Check: after `/memory dream --force` on the history store, compare `/memory stats` active bytes before and after, and look for parent plus source co-injection in the stage recall traces. Decide whether parents should be excluded from automatic recall when a source is selected, and add a separate reviewed-hypothesis arm if generalization is to be measured at all.

**3. High: short-term memory semantics are not exercised anywhere with a model.** Capture is off during task stages (`run.mjs:46`), the temporary prompt has no explicit expiry (`fixtures.mjs:20`), and the revoke prompt tells the model the override has expired (`fixtures.mjs:21`). Stages 1 and 2 also share one session, so the override is in the transcript regardless of memory. The only test of `retention: short` is the no-model temporal fixture in store-growth. The plan's "short term" arm is a different concept entirely: a recent transcript window. The user's question about short versus long-term memory needs both senses stated and tested. Recommended design: capture on during the temporary stage with an explicit "until ISO" expiry a few minutes ahead, then run the revoke stage in a fresh session without mentioning expiry, once before and once after the timestamp. That yields a clean 2 by 2 where the before case should apply the override and the after case should not.

**4. Medium-high: background scheduling contradicts the documented trigger.** The 1 MB soft trigger in `src/dream.ts:160` is bypassed because `index.ts:80-83` calls dream with force whenever consolidation is due, and the first saving capture with two project sources is always due since the schedule timestamp starts at zero. Two different active-byte definitions exist: serialized files, project scope only, in `index.ts:75`, versus title plus summary plus body across both scopes in `src/dream.ts:155`. The dream call runs inside the capture promise, so `session_before_compact` at `index.ts:144` can wait on a 60-second model call, and any new prompt aborts it (`index.ts:116`), which writes an incomplete report (`src/dream.ts:242`) and retries the full model call next time. An active user can pay for repeated aborted dreams. The eval sidesteps this with the dream flag set to zero, so production behaviour is unmeasured. Recommend decoupling dream from the compaction and shutdown paths, adding a minimum idle delay and backoff on aborted reports, and unifying the byte definition.

**5. Medium: budgets will dominate completion.** The default job wall clock is 180 seconds for all four stages (`run.mjs:13`, `:109-112`), and one 24-request file spans every stage (`run.mjs:101`), with `guard.ts:10` killing the process mid-stage on exhaustion. Expect most runs to be incomplete regardless of arm, which collapses the primary metric into "which arm ran out first". Fewer wasted requests is a real memory benefit, but it should be reported separately from completion. Recommend per-stage request and time budgets, the 600-second ceiling, and budget exhaustion as its own outcome category.

**6. Medium: context allowance is not equalized and a key negative control is missing.** The plan requires a common context allowance, but long and dream arms get the 600-byte window plus up to 1,200 bytes of recall plus the guidance system section (`index.ts:118`), the short arm gets 600 bytes, and the off arm gets none. There is no "extension loaded, empty store" arm, so guidance-prompt effects and recall effects cannot be separated, and cache-share comparisons are confounded by prefix length. The plan's distractor episodes, instruction-shaped tool output, and missing-approval controls are not implemented in history mode. Recommend adding the empty-store arm and reporting absolute uncached input tokens rather than cached share.

**7. Medium: scoring can be gamed and one guard setting needs a smoke check.** Action checks read report files the agent writes itself (`check.mjs:53-54`, `:96-97`, `:65`, `:108`). The CLI-run count at `run.mjs:128` matches only a filename, not the expected arguments or stdout. Tie each report to a traced bash call with the exact paths and compare the tool stdout JSON to the file. No check detects wrong-project policy use or global-scope leakage even though the plan lists both. Add assertions that ingestion creates no backups or recovery source file, migration creates no rejected.ndjson, and the captured store has zero global-scope items after history. Separately, `guard.ts:33` runs node with the permission model but without child-process permission. `node --test` spawns a child per file by default, so visible tests may fail with an access-denied error in every arm and burn requests. Verify in the smoke run and add `--allow-child-process` or `--test-isolation=none` if so.

**8. Medium-low, partly documented: size ceilings are never tested with a model.** The latest store-growth artifact fixed latency but same-scope precision is unchanged at 1,000 and 10,000 items (`bench/results/store-growth-v5.json:1715-1717`, `:2787-2789`), and the longitudinal stores will hold a dozen items, so the trigger never fires. A cheap polluted-store arm answers the ceiling question: seed the history store with the concentrated noise corpus in the same project scope and rerun stage 3 only.
